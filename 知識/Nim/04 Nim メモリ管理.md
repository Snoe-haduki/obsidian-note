# Nim メモリ管理

## 現在の基本

Nim 2.2.10の公式メモリ管理資料では、**ORCがデフォルトのメモリ管理戦略**である。

さらに、新しく書くNimコードには `--mm:orc` が推奨されている。

```bash
nim c --mm:orc main.nim
```

通常はデフォルトがORCなので、毎回明示する必要はない。設定を意識的に固定したい場合に指定する。

## メモリ管理戦略の選択

Nimでは `--mm:` スイッチでメモリ管理戦略を選択できる。

公式資料で中心的に説明されているのがARCとORCである。

## ARC

ARCはAutomatic Reference Countingを基礎とするメモリ管理方式である。

デストラクタとmove semanticsを利用する。

```bash
nim c --mm:arc main.nim
```

ARCはORCと基本機構を共有するが、サイクルコレクタを持たない。

大まかには、変数がスコープを外れたときにメモリが解放されるという考え方を追いやすい。

## ORC

ORCは参照カウントを中心とする方式で、参照サイクルを処理するcycle collection機構を備える。

```bash
nim c --mm:orc main.nim
```

ORCのサイクル処理はtrial deletionを基礎とする。

公式資料では、tracing型アルゴリズムを使用しないため、実行時の振る舞いがヒープやスタック全体のサイズに依存しにくい点が説明されている。

## ARCとORCの違い

簡略化すると次のように整理できる。

| 項目 | ARC | ORC |
|---|---|---|
| 参照カウント | あり | あり |
| move semantics | 利用 | 利用 |
| サイクル収集 | なし | あり |
| 新規コード向け公式推奨 | - | `--mm:orc` |
| 現在のデフォルト | - | ORC |

参照サイクルが発生し得る一般的なコードではORCを基本と考える。

ARCは、循環参照を避けられ、ライフタイムをより単純に追いたい設計で検討できる。

## 決定的なメモリ管理

Nim公式はARC/ORCについて、ハードリアルタイムシステムに適した決定的な性能特性を持つと説明している。

Nimが組み込みやリアルタイム寄りの用途で注目される理由の一つである。

ただし、「Nimを使えば自動的にリアルタイム保証が得られる」という意味ではない。

アロケーション、OS、スケジューリング、外部ライブラリなど、システム全体の設計は別途必要になる。

## ARC/ORCの最適化確認

NimコンパイラはARC/ORC関連の参照カウント操作を最適化する。

公式資料では、最適化結果を調べるために `--expandArc` を利用できる。

```bash
nim c --expandArc:functionName main.nim
```

またはモジュール単位で確認できる。

```bash
nim c --expandArc:fileName main.nim
```

性能上重要な処理で、コンパイラがどのようなARC/ORC変換を行ったか調査するときに使う。

## 私のプロジェクトとの関係

ゲームエンジン、暗号通貨ノード、OS、LLM推論基盤のようなプロジェクトでは、メモリ管理方式を「Nimだから自動で安全」と考えるべきではない。

各データ構造の所有関係、共有範囲、スレッド境界、アロケーション頻度を設計した上でORCまたはARCを選ぶ必要がある。
